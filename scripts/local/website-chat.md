# Website Chat

The public floating assistant uses the current `facebook_settings.rules_json` on every message. Keywords, category templates, and guided replies are shared with Messenger. The website contact prompt is edited in Facebook Automations → Reply rules. Messenger delivery switches do not disable website chat. Blank website category replies use General, then a fixed contact reply.

The website reuses Facebook's parsing, command, room suggestion, availability, checklist, and template functions. Its session orchestration is separate because its final action opens the existing booking form instead of creating a Messenger booking. Facebook wrappers and existing transport behavior remain intact. CONFIRM opens a form containing both dates, exact times, room, guests, full name, email, Philippine mobile number, activities and notes. Optional fields default to none. Visitors can write `Activities: ATV` and `Notes: Family celebration`. They submit the form themselves; only then is a pending request saved. Current catalog and availability are checked again on submission. The booking reference is deterministically derived from the random draft token, backed by the existing unique reference constraint, to prevent duplicates even after a process crash.

Only confirmed and checked-in bookings reduce availability in the assistant and public calendar. Pending requests are not room holds. Physical room assignment and staff approval remain the existing admin workflow. Published saved prices are used by the assistant; the existing form estimate remains explicitly labelled as preview/mock pricing.

Chat uses a separate HttpOnly, SameSite=Strict session cookie with no persistent lifetime. Session access expires after two hours without activity. At most 30 messages are kept in PHP session storage; no transcript table or browser storage is added. PHP's session garbage collector handles expired storage. Reset clears conversation data and invalidates outstanding drafts. Drafts expire after 30 minutes. Chat mutation and chat-origin form submissions require a session CSRF header. Chat submissions are serialized by the PHP session lock, and an IP-scoped database lock protects message rate counting across sessions (6/minute, 30/hour). The existing 5/hour public booking limit also applies. Reverse proxy deployments may aggregate IPs under REMOTE_ADDR; do not trust arbitrary forwarded-IP headers to bypass this limit.

Handoff offers existing email, Facebook and booking-form contacts. Website transcripts are not in the admin inbox. No staff live-chat delivery is implied; customized shared handoff text should reflect the resort's actual support process. Website requests appear in normal booking administration.

## Gemini configuration

### Optional shared booking interpretation

Set `GEMINI_BOOKING_INTERPRETER_ENABLED=1` deliberately to enable the shared website/Messenger interpreter; it defaults to disabled. The existing `GEMINI_API_KEY` and `GEMINI_MODEL` are reused. Deterministic parsing runs first. Eligible incomplete booking messages and unmatched inquiries can send the sanitized current text, non-sensitive booking fields, Manila date, and published accommodation/activity names to Gemini. Names detected locally, contacts, references and labeled private notes are removed; profile identifiers and chat history are never included. Automated detection cannot guarantee removal of arbitrary personal information in free text. Review account data-use terms before enabling visitor traffic.

The model returns structured candidates with source evidence. It also identifies informal Filipino/Tagalog or Taglish resort questions as `faq`, even without conventional wording or a question mark. A FAQ does not change a booking draft or clear an outstanding clarification. PHP checks the schema, evidence, dates, guest count, times, and catalog membership. Explicit booking fields cannot be reclassified as FAQ. Conflicts and ambiguities prompt clarification and block confirmation until resolved. Existing prices, availability, booking validation and staff approval still apply. Provider calls have a six-second timeout and a shared 300-calls/hour ceiling; failures and exhausted budget use deterministic behavior. Messenger receives no new free-form AI answers; it uses the shared intent to choose a safe rule-based support reply. Website Q&A remains a separate fact-grounded Gemini answer.

Messenger conversation work uses the existing worker after webhook acknowledgement. Apply `database/migrations/015_facebook_conversation_jobs.sql` through the maintenance account before enabling Messenger interpretation. Without it the webhook retains deterministic processing. `scripts/operations/setup-booking-interpreter.php` is a local-only convenience command and requires ALTER permission; do not grant that permission to the runtime account just for this setup. Interrupted conversation jobs recover after two minutes; failed conversation jobs block later conversation jobs for that sender until reconciled. Conversation application and reply queueing commit together, and a changed conversation revision discards stale AI results.

Run `C:\xampp\php\php.exe scripts/local/test-booking-interpreter.php` alongside both channel regression suites. It uses mock provider responses and rolls back Messenger fixtures. After migration 015, run `C:\xampp\php\php.exe scripts/local/test-booking-interpreter-worker.php` to verify that a queued conversation creates one reply job without contacting Meta. Real provider and Meta delivery checks are separate.

Set `GEMINI_API_KEY` in your untracked local `.env` and separately in the production environment. `GEMINI_MODEL` defaults to `gemini-3.8-flash`; select a supported model available to your Google project. Do not put these values in `VITE_*` configuration. A missing key keeps the rule-based assistant usable.

PHP calls the fixed Google HTTPS generateContent endpoint using cURL with TLS verification, a 3-second connection timeout, 10-second total timeout, and bounded request/output context. Enable PHP cURL and outbound HTTPS on Z.com. No browser dependency, worker or public tunnel is required. Deploy the compiled frontend plus updated API/includes files together. No schema migration is needed.

Website support questions, including side questions during an active booking, may use Gemini. The support reply answers from published resort facts, matches the visitor's language, and offers one relevant next step toward an inquiry or booking without pressuring the visitor. Gemini receives selected public database facts, a redacted current question, and only non-sensitive booking progress (whether a booking is in progress, dates and guest count); never booking transcripts, names, contact records, booking references or arbitrary SQL tools. This lets the agent avoid repeatedly asking for already-known details. Questions containing detected contact information or explicit identity introductions bypass AI. No earlier chat history is sent to the provider. Provider failures, blocked/empty/truncated responses and missing credentials fall back to a shared rule-based reply. Responses use plain text. Review Google API data-use terms for the account tier before enabling real visitor use; user-entered free text may contain information that automated detection cannot identify. Avoid entering sensitive personal details in general questions.
