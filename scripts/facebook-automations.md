# Facebook Automations — local workspace

The admin navigation includes **Facebook Automations** immediately below Website Content. It uses the existing admin session, CSRF protection, Vite `/api` proxy, and PHP/PDO database connection. Verified Messenger messages are categorized and their approved templates are queued automatically. Manual test entries remain blocked, and draft approval does not publish a post.

## Setup and verification

With the existing local Apache/MySQL services running:

```powershell
C:\xampp\php\php.exe scripts/setup-facebook.php
C:\xampp\php\php.exe scripts/test-facebook.php
npm run build
```

Setup checks the additive Facebook tables, including the stateful conversation table from migration 009, in the local `odidepse_db` using its configured application account. It creates missing tables only if that account has schema privileges, preserves existing rows, and reports booking counts before/after. If CREATE permission is unavailable, apply the SQL through the local database administration connection (for example phpMyAdmin); do not substitute root credentials in the application. The test uses a transaction and rolls back its own rows.

For a later authorized Z.com release, apply migrations 004 through 009 in order after migrations 001 and 003, and apply migration 012 before deploying chatbot room-combination support. Then deploy the changed PHP and compiled frontend together. Keep setup/test scripts and this document out of `public_html`; follow `DEPLOYMENT_WORKFLOW.md`. Configure the documented Meta environment values separately; never upload the local `.env`.

## Available workflows

- Messenger: new webhook inquiries are classified by English, Tagalog, and Taglish keywords. Exact phrases are preferred, followed by conservative typo matching for single words of at least five characters. A recognizable stay date together with a labelled party size is treated as booking intent even without the words “book” or “available.” Booking inquiries ask for dates, guest count, optional room preference, full name, and email or phone together so the customer can provide everything in one message. The assistant accepts natural English/Filipino dates and numeric or written guest counts (including combined adults and children), then proposes a suitable available room and saved rate; when the room is omitted it selects the best-fitting option for review. A rates-only inquiry asks for dates and guests together, returns suitable options, and lets the customer continue by sending the option, name, and contact in one message. If an accommodation has no saved price, the assistant says staff will provide the rate rather than inventing one. Partial answers are remembered and all remaining items are requested together rather than as a rigid sequence. `MENU`, `BACK`, `RESTART`, `CANCEL`, and requests for an admin are supported, including Filipino aliases and conservative command misspelling tolerance. Rates, amenities, and location questions are answered without losing booking progress. Manual entries are explicitly labelled and never establish Messenger sending eligibility.
- Booking safety: the assistant shows a final summary and requires `CONFIRM`. An automatically selected accommodation is clearly labelled as a suggestion based on group size and availability. If the selected stay has configured room photos, up to three are uploaded consecutively as native Messenger image attachments so customers can open them in Messenger's photo viewer. Each photo waits for the previous delivery, and a short message is released only after the final photo succeeds; it identifies the room as either the suggestion for that group size or the room the customer explicitly requested. Messenger may visually group consecutive photos depending on the client, but the Send API does not provide a guaranteed album operation. Incomplete replies show a checklist of every received field and request only the missing values. The assistant creates only a pending booking and a staff alert; staff must review and manually confirm it. Complaints, unsupported requests, and groups with no suitable listed accommodation are handed to staff. When the same customer sends revised details while their linked booking is still pending, the assistant preserves its reference and contact details, rechecks availability without counting that request against itself, and updates the same booking only after another summary confirmation. Confirmed, checked-in, completed, or cancelled bookings are never changed automatically and are handed to staff.
- Reply rules: save classification, automatic reply, and comment alert preferences plus category templates. A collapsed advanced panel allows up to 40 comma- or line-separated English, Tagalog, or Taglish keywords per category without crowding the normal rules form. A second collapsed panel exposes every guided booking reply as a separate client-editable field. Dynamic room choices, customer data, the pending reference, and the mandatory staff-approval warning remain controlled by the server. Complaint keywords take priority and General is the fallback. Automatic replies are enabled by default. Complaints receive only the configured acknowledgement and remain flagged for a person; a blank category template skips that category's automatic response. Updates apply to new intake, not historical items.
- Automatic disclosure: automatically delivered Messenger messages end with a fixed notice that they are system-generated and that the customer can reply `ADMIN` to reach a person. Staff replies and the admin-handoff acknowledgement omit that redundant notice.
- Comments and staff alerts: record comments; see new-comment and complaint flags across all inquiry types in Staff alerts. Clear attention after acknowledging. Comments are private by default; an admin can publish or hide each comment on the homepage. The public API exposes only the display name, original text, and received date. Alerts are in-app and refreshed on page navigation or Refresh; no email, push, or background polling is enabled.
- Leads: record guest contact details and inquiry text. Facebook item IDs are optional but deduplicated when supplied. Open the existing booking form, review guest details, choose dates/stay, and save a pending booking. Lead linking and booking insertion share one transaction and lock the lead to prevent double conversion. Leads and public inquiries never imply a confirmed reservation; an admin must confirm a pending booking. Incomplete leads remain in the lead inbox.
- Post drafts: write a caption or generate one using a fixed introduction, supplied details, and call to action. This is template generation without an AI provider. Review, approve, reject, and edit drafts. Edits clear approval; revision checks prevent stale approvals. Publishing remains disconnected.
- Delivery queue: inspect automatic and staff-prepared replies; cancel a queued job. A cancelled reply can be prepared again, but an active/sent job is deduplicated by inquiry. Changing a category or resolving an inquiry cancels outstanding replies.
- Audit: immutable through the API, metadata-only actions with actor/entity IDs and timestamps. Inbox/draft content is held separately in protected tables. Lists are paginated in sets of 25.

## Meta connection and delivery

Implement a verified Meta webhook adapter, then reuse/refactor the intake workflow for trusted events. Manual IDs must be reconciled with live IDs without establishing trusted message timestamps from manual records. Store only the contact/content fields the workflow needs, and define retention with the owner before live customer intake.

The public callback is `/api/facebook-webhook.php`. Configure Meta app/Page credentials server-side, HTTPS verification and webhook signature checks, correct Page identity, subscriptions and permissions, duplicate-event handling, and lead-detail retrieval. The Cloudflare preview launcher runs the worker every second while its window remains open. On production hosting, run `php scripts/facebook-worker.php` every minute from cron to resolve the sender's display name and deliver eligible automatic replies. If Meta does not return a name, the inbox retains the `Messenger guest` fallback. Lead events remain blocked until lead-detail retrieval is completed. The worker rechecks source, Page, conversation age, status, category, and template at dispatch; manual entries and old queued replies never become eligible just because the connection is enabled.

After a staff reply is successfully delivered from the website inbox, automatic replies for that Page customer pause for 24 hours. Incoming messages remain recorded during the pause. The next customer message after expiry starts a fresh chatbot conversation, while `RESTART` resumes automation immediately.

Add the cPanel worker during an authorized production deployment. Jobs use atomic claims, attempt increments, stale-claim handling, and rate-limit handling. `facebookRetryDecision()` and `facebookRecordFailure()` provide bounded exponential backoff (up to five attempts), Retry-After handling, terminal errors, and audit recording. Unconfirmed sends require reconciliation before any retry.

External notification delivery, AI-generated captions, automatic lead-form conversion, and scheduled publishing are separate additions; this workspace supports stateful Messenger booking requests, staff-reviewed confirmation, and template-generated drafts.
